# Working on the MCP server

This directory is its own npm package, independent of the Astro site. Use **npm** here
(not yarn), and run everything from `functions/`:

```bash
npm run lint && npm run format:check && npm run typecheck && npm test
```

`oxlint` enforces most of what follows — including a custom plugin in `lint/` — so run it
rather than trusting a read-through.

## Conventions the linter enforces

- **One object parameter.** A function with more than one parameter takes a single
  destructured object: `fn({ agenda, session })`, never `fn(agenda, session)`. Inline
  callbacks are exempt.
- **Named types live in `<module>.types.ts`** next to the module. A `.types.ts` file holds
  nothing but types. Object types nested inside a signature must be named too.
- **At most 8 files per folder** (subfolders don't count). When one fills up, group by
  feature, not by kind — that is why `tools/plan/`, `tools/browse/`, `tools/calendar/` and
  `tools/agenda/` exist.
- **Identifiers are at least 2 characters** (`i`, `z`, `_` excepted). No `s`, `r`, `e`.
- **Relative imports end in `.js`** even though the files are `.ts` (NodeNext ESM), Node
  built-ins use the `node:` prefix, and exports are named — no default exports, no barrel
  files.
- Braces always, no nested ternaries, blank line before `return` and after an `if` block.
- Keep functions under 120 lines, files under 300, complexity under 15, nesting under 3.

## Tests

- Flat: **no `describe`**. Start the test title with the topic instead
  (`it("search resolves human day names", …)`).
- **No `vi.mock` / `vi.spyOn`.** Run the real modules and fake only the outside world with
  a recording fake in `test/fakes/` (see `recorded-log.ts`).
- Tests never hit the network: `REVERSIM_OFFLINE=1` in `vitest.config.ts` makes them run
  against the bundled snapshot.
- A change under `src/http/` comes with a test in `test/security.test.ts`.

## Layers

Imports only point down this list:

1. `src/index.ts` (the Cloud Function) and `src/dev-server.ts` — thin wrappers around
   `handleMcpHttp`
2. `src/http/` — body limits, auth, origin checks, rate limits, headers
3. `src/server.ts` — MCP tool/resource/prompt registration
4. `src/format.ts` — results into MCP content
5. `src/logic/` — pure functions over an `Agenda`: no I/O, no `fetch`, no `process.env`,
   no logging; imports only types from `data/`
6. `src/data/` — fetching, validating and normalizing the feeds, plus the snapshot
7. `src/metrics/`, `src/config.ts`, `src/errors.ts` — leaves anything may import

`process.env` is read only in `src/http/`, `src/metrics/`, `src/data/agenda.ts` and the
entry points, always with a checked default. Every new variable goes in the README.

## Things that will bite you

- **Never leave work running after the response.** Gen 2 functions run on Cloud Run, which
  throttles the CPU once the response is sent, and there is no `waitUntil`. A pending
  promise can stall until an unrelated later request wakes the instance, or vanish.
  Metrics are written synchronously for this reason.
- **The request body is already read** by the platform into `req.rawBody`; iterating the
  stream yields nothing. `readBody` handles both paths — don't "simplify" it.
- `src/data/snapshot.ts` is generated by `npm run update-snapshot`. Never edit it by hand.
- Throw `UserError` only for messages that are safe to show a client. Everything else is
  logged server-side and answered generically — no stack traces, no upstream URLs.
